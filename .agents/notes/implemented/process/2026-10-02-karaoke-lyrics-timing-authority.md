# Agent Note: 逐字时间以网络逐字歌词为权威，CTC 只用于定整体平移

Status: implemented

Decision-ID: karaoke-lyrics-timing-authority


## Code

- `.agents/skills/hx-anime-karaoke-ass/scripts/gate/check_gates.py`
- `.agents/skills/hx-anime-karaoke-ass/scripts/grid/check_timing_health.py`
- `.agents/skills/hx-anime-karaoke-ass/scripts/kf/kf_timing.py`

## Problem

用户反馈「按字它没有非常准确，总有几处，由于长音之类的关系导致识别不准确」。这不是主观感受。

CTW 强制对齐（`align_ctc.py`，wav2vec2 平假名 + Viterbi）在**长音与间奏**处会塌缩：
它把一个音拍当一个状态段，当歌手把某音节拖长、或句中夹着间奏时，CTC 把整段时间**全部**
算给最后那个音拍，其后的音拍起点被整体顺延。

实测 `proj-touhou`（东方《果てなき風の軌跡さえ》），36 行里 8 行如此，最坏一行：

```
纯 CTC  行27「教えてくれた」 首 166.160  尾 188.930  跨度 22.77s
真值（原作者手工锚点）        首 166.220  尾 167.720  跨度  1.50s
```

**15.2 倍**。其中「れ」独占 12.17s，而那段时间（176.3~188.5s）的人声能量只有 **-34.4 dB**（间奏）。
字级统计：纯 CTC MAE **0.2595s**、最大 2.948s、90 分位 0.399s。

更糟的是这个错误**已经漏进了成片**：当时的 `check_timing_health.py` 正确报出了这 2 处塌缩
（报告里写着"应为 0"），但它**只打印、退出码恒为 0**，`fixes.json` 只写了一条，
没有任何门禁去读这份报告，于是那句歌词比声音晚了 20 秒交付。

## Decision

把「逐字时间」拆成两个**互相独立**的量，分别用最可信的来源：

| 量 | 来源 | 实测依据 |
|---|---|---|
| **句内相对形状** | LDDC 网络逐字歌词 | 与作者手工调准的音拍句内间隔差 **中位 5ms、最大 9ms** |
| **整体平移** | 本地 CTC 行首 | 唯一由"这份视频"决定的东西；单调、中位数可吸收抖动 |

`kf_timing.py fetch` 走 LDDC 抓逐字（QM/KG/NE/LRCLIB），存 `kf.json`；
`align` 用 `SequenceMatcher` 把逐字序列与歌词音拍序列（都转平假名）对齐，
得到句内相对形状，再叠上本地行首锚点，产出 `timing_kf.json` 与 `review/kf-report.md`。

**四条实测纪律（违反会显著变差）**：

- **用全部行取中位求偏移，不剔除塌缩行**。剔除后 +1.9475s（真值 +1.901s，误差 46ms）；
  用全部行 +1.9190s（误差 18ms）。塌缩发生在**行尾**，行首那一拍仍然准，剔除是白丢样本。
- **绝不把每行各自的 CTC 行首当锚点**（除极少数结构性离群行）。实测逐行锚定 MAE 0.2918s，
  单一全局偏移 0.0307s  **差 9.5 倍**。CTC 行首的抖动是全曲性的（每行都在抖，中位偏离 0.191s、
  最大 0.758s），挑"偏离大的行"让它们用自己的行首，等于专挑最不准的测量值当锚点。
- **对齐坐标系必须用显示文本（`surf`），不能用注音**。踩过的坑：一字多拍（「人」=ひ+と）时
  曾用假名占位，结果坐标系从汉字换成假名，与 LDDC 的原文对不上，**整行从第二个 unit 起全部错位**
  （实测 MAE 0.244s vs 正确写法 0.023s）。正确做法是让同字的多个音拍**共享同一个字符下标**，
  对齐后再按「下一字符时间 − 本字符时间」在字内均分。
- **逐行偏移是否需要中位滤波，要按数据自适应**。判据是「偏离全局值 >2s 的行占比 ≥5%」：
  这类行是**前句塌缩把后句整体推后**造成的（实测 `tsunagukizuna` 行 7/8/17 分别偏
  4.62/3.55/3.73s），用邻行共识的中位能吸收；而抖动小的工程（touhou 最大偏离仅 0.754s）
  一滤波反而从 0.0307 退化到 0.1073s。**用 90 分位当判据会误触发**（touhou 的 90 分位
  是 0.570s，被 19% 的少数行抬起来），必须用"2s 以上的占比"这种量级判据。

同时把体检从"报告"升级为"门禁"：`check_timing_health.py` 现在在
（CTC塌缩 > `--max-collapse` 默认 0）或（句内间奏 > `--max-inner-silence` 默认 0）时
**非零退出**；`check_gates.py --stage render` 读 `review/health.txt` 的**判定行**（不是"文件在不在"）。

## Alternatives considered

- **什么都不做 / 继续只用纯 CTC + 人工校时**：最强理由是「抽看频谱本来就能发现长音问题，
  加一条外部数据源是引入依赖」。否决：实测这个"能发现"没有兑现  报告里已经写明了塌缩，
  它照样进了成片。人工校时的瓶颈不是判据缺失，而是判据不被强制执行。
- **把 LDDC 逐字当唯一来源，完全不用 CTC**：最强理由是「既然相对关系权威，整体也可以直接信」。
  否决（实测）：LDDC 的时间轴属于**另一份音源**，与手上的视频差一个常量（本例 1.901s），
  且这个常量**无法从音频独立估计**  我试过谱通量起音投票法，被周期性段落吸到 +4.0s 的伪峰
  （真值 +1.901s）。必须由本地对齐提供平移。
- **用多个歌词源投票取一致**：最强理由是「用户在任务里建议了多音频比对」。否决（实测）：
  **QM 与 KG 对同一首歌返回的逐字时间完全相同**（句内间隔差恒为 0），即它们共享同一数据源，
  投票没有信息量；NE 是独立采集但版本常有出入（同一首歌差 0.2~12s）。所以多源是
  **覆盖关系**而非投票关系：只把它当"这首歌在哪个源能拿到"来用。
- **逐行缩放（把逐字节奏拉伸到本地行时长）**：最强理由是「本地行时长本身就反映了这份视频的语速」。
  否决（实测）：本地行时长在塌缩行里是**被污染的**（22.77s vs 1.50s），拿它做缩放因子
  会把塌缩放大。实测逐行缩放版 MAE 0.607s，比纯 CTC（0.260s）还差。
- **继续只打印报告、靠 agent 自觉读**：否决。这正是本次事故的成因，见 Problem 末段。

## Consequences

- 实测改善（字级，对同一 ground truth）：MAE **0.0307s**（中位 0.025s、90分位 0.051s）
  vs 纯 CTC 0.2595s，**8.4 倍**；长音字单独看：0.580s → **0.011s**。
  另一路同口径测量（LDDC 字级时间 + 全局偏移 vs 作者锚点）给出 MAE 0.0228s、最大 0.081s，
  即本实现的 0.0307s 基本贴住这条链路的**物理上限**（差距来自字内均分与池兜底行）。
- 塌缩行不再是问题：该组字 MAE 0.0260s（正常行 0.0336s），即融合后塌缩行与正常行同质。
- 体检从"报告"变"门禁"后，同一工程实测：旧 `timing.json` EXIT=1（塌缩 2、句内间奏 3），
  新 `timing_kf.json` EXIT=0（塌缩 0、句内间奏 0、过长音拍 30→2）。
- `kf_timing.py fetch` 依赖 HX-Music 的 `pyTool`（LDDC + PySide6），**不在本仓**；
  `--lddc` 或 `HX_LDDC_PATH` 指定。LDDC 的 `g2p_en` 需要 nltk 语料、离线会被拦，
  纯日语歌曲直接 stub（脚本已处理）。缺 `kf.json` 时 `align` 明说"不做任何事"，不伪造。
- 已知边界：LDDC 给的是**字级**时间，音拍多于汉字时按句内插值摊开（拗音「じょ」为一拍两字符，
  脚本按字符对齐后收回到音拍首字符）。所以它的价值在"句内节奏"，不是"逐音拍绝对精度"。
- `check_gates.py --stage render` 从此会因缺 `review/health.txt` 而 FAIL 
  存量工程需要补跑一次体检（这是有意的：那份报告本来就该存在）。
