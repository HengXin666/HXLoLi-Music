# Agent Note: 特效设计维度从 3 格扩到 15 格, 并让门禁真的查它

Status: implemented

Decision-ID: karaoke-design-15-cells


## Code

- `.agents/skills/hx-anime-karaoke-ass/scripts/gate/check_gates.py`

## Problem

用户对 `11-design` 提出两条意见, 都指向"设计维度本身不够":

1. **每句的上下文关联**: 相邻两句之间能不能有关系.
2. **同一句内颜色不分**: 前半句与后半句、主唱与和声, 现在全是一个颜色.

实测确认这不是"没做细", 是**维度缺列**:

| 量 | 实测(漆黑子弹 ED / 33 句 / 2026-10-03) |
|---|---|
| fx 首事件 == 该句 band 起点(±0.05s) | **31/33** |
| fx 末事件 == 该句 band 终点 | **33/33** |
| 每句图形种类(按绘图路径 md5) | 中位 **4**, 最小 1 |
| 每句 fx 事件数 | 中位 **80**(参考量级 OP=19/ED=17 的 4.4 倍) |
| fx 事件终点晚于下一句 band 起点 | 31.3%(但那只是 `Generator` 的退场淡出尾巴, 不携带任何变量) |

**每句的视觉变量生命周期被钉死在本句**, 句间没有任何量是连着的  这就是"读起来是 33 个独立片段"的根因,
与密度无关(密度已是参考的 4 倍).

第二条更直接: `anim.py::Karaoke.colors()` 只有 `th["hi"]` 一个来源(除非传 `hl_color`),
而设计表**根本没有副文本的列**  `rb_ent` / `cn_ent` / `cn_delay` 三个旋钮在库里存在,
33 句却全部走默认值(注音永远晚 0.06s、中文永远晚 0.20s).

而旧表写的判据「一句里不同图形种类 ≥6」**从来没有被任何门禁查过**, 所以中位 4 照样 13 步全绿交付了.
**门禁不管的判据 = 不存在的判据.**

## Decision

把"设计维度"显式化成 **3 个文本对象 × 5 个生命阶段 = 15 格**, 并把其中 5 项变成可失败的检查.

1. **轴 A 文本对象**: 主文本(日文行) / 副文本(注音·中文·合いの手) / 背景.
2. **轴 B 生命阶段**: 出现 / 逐字 / 词组关联 / 意象 / 消失.
   五档都能指到库里**已有**的机制(`ent`·`hl`/`hl_kind`·`seq`/`find`/`line.py`·`props.py`·`ext`),
   不是新造的概念.
3. **`check_design`**(默认 WARN, `--strict-design` 升 FAIL)查五条:
   15 列齐全且每格**要么填要么写 `—`**(空串=忘了做, `—`=决定不做, 必须区别);
   `主·逐字` 取值 ≥3 种; `副·出现` 取值 ≥3 种; `副·逐字` 填写率 ≥50%;
   `承上` 与上一行 `启下` 有**同名变量**的行 ≥60%; `背景·场景` 填写率 ≥70%.
   样本 <4 行时只给 WARN  用 2 行表去数"取值种类"的分母不可信.
4. **承接必须是变量**: `impl/thread.md` 定义五种可核对类型(节奏/语法/意象/位置/色温承接),
   并写明"时间上重叠"不算承接  实测那 31.3% 跨句事件色相/位置/图形都不变, 只是 alpha 在降.

**背景层不是全屏**: band 铁律不变. 专业参考(东方 `orig_ref.ass`, 42872 事件)的背景样式
`Ptcl` x 372–1392 / y 856–972, 逐秒覆盖 61%; `Flow` 覆盖 78%; 跨句事件只有 1.2%.
所以"背景贯通"的正确形式是**图形与配色全曲统一 + 覆盖率铺到句间空隙**, 不是长事件跨句.

## Alternatives considered

- **什么都不做, 靠人工审"有没有承接感"**: 最强理由是承接是审美的、机械判会逼出表演性的填写.
  否决: 实测的两条失败(每句重起、副文本从未设计)都**完全可以机械数出来**  数第一句 fx 起点
  是否总等于 band 起点、数副文本旋钮是否全曲同值. 审美判断留给主母题选得对不对
  (这一条门禁本来就不查, 见 `2026-10-02-karaoke-elements-table-gate.md`).
- **直接把"句子之间要有承接"写进文档**: 否决. 这正是旧判据「图形种类 ≥6」的失败模式 
  它写在 `three-layers.md` 里, 没人执行, 也没人发现它没被执行.
- **颗粒度继续变细, 一句拆成多行(按字/按词)**: 最强理由是"更精确". 否决:
  用户明确说"不要再细了, 是维度不够"; 且逐字级信息已经在 `timing.json` 里, 表再细一次只是抄它.
  变的是**维度**(3 格 → 15 格), 不是分辨率(仍是一句一行).
- **把 `check_design` 直接设成 FAIL**: 最强理由是"WARN 等于没查". 否决(实测):
  现存 3 个工程的表都是旧格式(3 格), 直接 FAIL 会让 `check_gates` 在它们上永远红灯;
  默认 WARN + `--strict-design` 让新工程可以用严格档, 旧工程留在报告里可见.
- **拿"跨句事件占比"当承接判据**: 否决(实测): 本工程 31.3% 的事件跨句, 看起来很好,
  但它们是退场淡出的尾巴(色相/位置/图形全不变). 只查时间的判据会被这个数字骗过.

## Consequences

- 合成表正反验证: 4 行合规表在 `--strict-design` 下 6 项全 PASS;
  把副文本列留空、逐字列全填 `wipe` 的表, 5 项里 4 项 FAIL.
- 本工程 `check_gates.py --project dev/漆黑子弹/トコハナ --stage design` 现在报
  `WARN 还是旧格式(入/出/高亮 3 格)`, 其余 6 项仍绿  旧工程的可见归可见, 不阻断.
- `impl/three-layers.md` 仍然有效, 它管的是"同一个格子里图形叠几层"; 与本文是**先后关系**:
  先选对象与阶段, 再决定层级.
- 已知边界: `承上`/`启下` 的"同名变量"只做词元交集, 不理解语义 
  两行都写"留一条向右的动量"会判通过. 这是可证伪下限, 不是质量上限.
