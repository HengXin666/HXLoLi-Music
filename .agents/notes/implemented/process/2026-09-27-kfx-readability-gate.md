# Agent Note: KFX 可读性规则与对比度门禁

Status: implemented

Decision-ID: kfx-readability-gate

## Code

- `py/ass/check_contrast.py`

## Problem

ASS 特效歌词的配色此前没有可验证的判据，只靠肉眼看着"还行"就交付。

## Decision

ASS 特效歌词的配色不再靠肉眼判断，改为**渲染前先量对比度**。
规则写在 `doc/KFX-RULES.md`，检查器是 `py/ass/check_contrast.py`。

本篇只管**配色**这一条。特效密度与空间占用的判据是另一条决策，
见 [kfx-quality-redline](2026-09-28-kfx-quality-redline.md)。

判据取自 WCAG 2.1 原文（W3C），未加自创阈值：

| 对象 | 门槛 |
|---|---|
| 填充 / 描边 | ≥ 4.5:1 |
| 填充 / 背景 | ≥ 4.5:1 |
| 暗态填充 / 背景（仅"整行先出现"时适用） | ≥ 3:1 |

**为什么**

真实的失败记录，两次都是"看着还行"就交付：

1. 填充 `(232,244,255)` + 描边 `(168,216,248)`  两者只差 **1.36:1**，
   渲染出来轮廓消失、糊成一团。用户的原话是"文本看不清"。
   根因是**描边也是浅色**；描边亮度必须 ≤ 0.1833（纯灰 ≤ RGB 118）。
2. 未点亮的字用 `(46,40,34)` 打在 `(11,16,22)` 背景上，只有 **1.31:1**，
   效果是"整行没出现"而不是"整行暗着等待"。

共同点：**没有可验证的判据就去渲染，而且渲染完没有回头量。**
检查器建立后，同一套错误配色被自动判 FAIL（填充/描边 1.36:1）。

**检查器自身踩过的两个坑**

两条都会让检查器**给出错误的 PASS**，比不做检查更危险：

1. `lstrip("0x")` 是字符集不是前缀  `"0B1016".lstrip("0x")` 剥掉开头的
   `0B`，得到 `"1016"`，之后所有解析都是垃圾。
2. ASS `&HBBGGRR&` 与网页 `#RRGGBB` 色序相反  混用会静默对调红蓝。
   `0B1016` 当作网页色是 `RGB(11,16,22)`，当作 ASS 是 `RGB(22,16,11)`。

因此定了一条反验规则：**检查器给出 PASS 后，要拿已知答案的样本反验它**。
本项目的反验样本是 Charlotte 的梅紫 `#91276F`，应输出 填充/描边 ≈ 7.7:1。

## Alternatives considered

**什么都不做（继续靠肉眼调）**：最省事，且单次改动确实更快。
否决理由：已经连续两次把 1.36:1 的配色当成品交付，而且看渲染图时没看出来。
问题的性质不是"调得不够好"，是"没有回头验证"，靠肉眼无法自我纠正。

**只在文档里定规则，不写检查器**：规则文字已经足够说明"描边要够暗"。
否决理由：本项目的失败正是因为规则停留在描述层面（"要看得清"），
没有可执行的判据。一个能返回退出码的脚本才能接进流程、拦住改动。

**直接引入现成的对比度工具（如 `colorcontrast` 之类的库）**：不必自己维护色值解析。
否决理由：它们按网页 `#RRGGBB` 解析，而 ASS 是 `&HBBGGRR&`  正是本项目
踩过的那个色序坑。自己实现才能把 ASS 的两种色序都处理对。

**把规则放在 `~/.local/share/hx-kfx/`（用户级共享）**：可跨项目复用。
否决理由：用户明确要求迁进项目  放在用户目录里"全宇宙谁都加载不到"，
他自己都找不到。规则必须和它约束的产物在同一个仓库里。

- `py/ass/check_contrast.py` 新增

- `static/music/东方/果てなき風の軌跡さえ_双版混合.ass` 已按新规则重建配色
  （填充/描边 1.36:1 → 5.27:1）
