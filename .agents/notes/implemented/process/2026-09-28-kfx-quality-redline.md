# Agent Note: KFX 质量红线（静态拦截）

Status: implemented

## Problem

配色有了对比度门禁（见 [kfx-readability-gate](./2026-09-27-kfx-readability-gate.md)），
但**特效本身的密度与空间占用没有判据**。结果是能造出"结构完整、对比度达标、
却只有卡拉OK效果"的成品，而且它能通过所有现有检查。

真实失败记录（同一份成品，两轮人工评审）：

1. 只有 40 条事件、0 个绘图层 —— 用户的原话是「动效到底在哪呀？你就一个卡拉ok效果」。
2. 把特效铺满整个 1920×1080 —— 用户的原话是「你怎么能看用全屏呢？
   你就只能是在字幕旁边呢，那我截取吹我还怎么看字幕，字幕这么小」。
3. 体积 0.91 MB —— 用户的原话是「体积小于 10MB 的全部都是垃圾」。

三者的共同点：**看不出错在哪，因为没有任何判据说它错。**
现有验证器（参照项目的 `validate_kfx.py`）只检查**结构完整性**
（编码、样式存在、时间戳格式），它给这三份成品都判了"验证通过"。

## Decision

建立 `py/ass/quality_gate.py`，作为交付前的**静态红线**。退出码非 0 即拒绝交付。

判据全部来自**实测对照**，不是自创阈值。对照物是参照项目里的真实成品
`assets/案例/Bravely You/成品_KFX.ass`（用户指定为"原版"）。

**红线（FAIL）**

| 判据 | 阈值 | 来源 |
|---|---|---|
| 事件数 | ≥ 3000 | 对照成品 5211 |
| 体积 | ≥ 10 MB | 用户明确要求 |
| 图层数 | ≥ 5 | 对照成品 5 |
| 样式数 | ≥ 5 | 对照成品 31 |
| 每事件 `\t` 均数 | ≥ 2.0 | 对照成品实测 1.60，向上取整 |
| 动画事件占比 | ≥ 90% | 对照成品 99% |
| **画面中部占用** | ≤ 5% | **对照成品 0.0%** |
| 注音层 | 必须有 | 日语歌词的硬需求 |
| 中文层 | 必须有 | 用户明确要求 |
| 描边色种类 | ≥ 2 | 单色 = 无色彩叙事 |
| 描边亮度 | ≤ 0.183 | 继承可读性门禁 |

**黄线（WARN，需说明理由）**：粒子数、旋转标签数、绘图事件数、遮罩事件数。

**空间判据的依据**

对照成品的实测空间分布（PlayRes 1280×720）：

```
y=  0- 80    3005 条   ← 中文（顶部）
y=560-720    2170 条   ← 日文 + 注音（底部）
y= 86-396        0 条   ← 画面中部, 完全空置
```

**它一点都不碰画面中部。** 这是"字幕特效"与"MV"的分界：
字幕特效只能待在文字带附近，遮住画面主体就等于毁掉观看。

因此判据是「画面中部（12%~55% 高度区间）占用的坐标点比例 ≤ 5%」，
而不是"y 坐标必须小于某个值" —— 前者对任意分辨率都成立。

**为什么只用文字层判描边亮度（这条判据改了四版）**

初版把所有 `\3c` 都算进去，于是光晕层的装饰色被判 FAIL —— 但它 `\bord0`，
根本**没有描边**，用可读性门槛卡它是判据用错对象。

第二版改成样式名白名单（`JP` / `TextDim` / `CN` …），结果**一个都匹配不到** ——
各作品命名毫无规律，参照成品的样式叫 `"OP JP 6-furigana"`（带空格），
另一个叫 `"S3"`。名字不可依赖。

第三版改成结构性判据：**凡被事件引用、且该事件去掉 override 块后仍有可读字符的样式，
算文字层**。这版又漏了 —— 绘图层（`MagicLine`）的文本是 `"m 740 320 b ..."`，
去掉 override 块后那些坐标**看起来就是"可读字符"**，于是它 `\bord0.6` 的
亮色装饰被当成文字描边判 FAIL。

第四版（现行）加入**绘图路径识别**：把 `[mnlbspc]` 后跟一串数字的片段全部剥离，
若剥完为空则判定为绘图事件，不计入描边检查。
同时 `\bord0` 或样式表 Outline 宽度为 0 的事件一律跳过。

**这个演化本身是教训**：白名单、名字约定、文本长度都不可靠；
只有**从语法结构反推语义**（`\bord` 才是描边、`\p` 绘图模式后跟坐标就是图形）
才跨作品成立。

**为什么阈值要留余量**

主色一开始定在 L=0.1831（上限 0.1833），判 FAIL。差了 **0.0002** —— 纯浮点边界。
阈值贴着上限时，"刚好达标"和"刚好超标"无法区分。
改法：派生颜色时把目标定成上限的 92%（L ≤ 0.169），留出余量。

**反验要求（继承自可读性门禁）**

检查器必须拿已知答案的样本反验。本项目的反验样本是对照成品本身——
它应当**在体积与中文层上 FAIL**（1.00 MB、中文 0 事件），
因为它是 720p 的 OP 而非本项目要交付的成品。若它全项 PASS，说明判据失效。

## Alternatives considered

**什么都不做（继续人工评审）**：已经有人在评审，且人工能发现"太土"这类判据难写的问题。
否决理由：人工评审发现的三个问题（无特效、铺满屏、体积小）**都是可机械检测的**，
而人工评审漏过它们三轮。人工的注意力应该花在"好不好看"上，
不该花在"数一下有几条事件"上。

**只写检查清单文档，不写检查器**：清单更易读，也不会有误报。
否决理由：这正是可读性门禁踩过的坑 —— 规则停留在描述层面就没人执行。
一个能返回退出码的脚本才能挂进流程。

**直接扩写 `validate_kfx.py`**：不必维护两个检查器。
否决理由：那是参照项目的文件，它的职责是**结构完整性**（模板前状态能不能被
Aegisub 消费）。质量判据是另一件事，混在一起会让"结构对但质量差"被
"结构校验通过"掩盖。两者职责不同，分开维护。

**把阈值定成"越高越好"（例如事件数 ≥ 10000）**：能一次逼出更厚的成品。
否决理由：对照成品只有 5211 条事件却质量合格，说明**厚度不等于质量**。
阈值应该定在"低于它一定不合格"的位置，而不是"达到它一定合格"。
本门禁只负责拦下限，上限由设计负责。

## Consequences

- `py/ass/quality_gate.py` 新增
- 东方成品已通过红线（42782 事件 / 20.56 MB / 9 图层 / 中部占用 1.8%）
- 配色按本门禁重推：`#60C878`(2.09:1) / `#A0FFC0`(1.20:1) / `#D0FFE8`(1.10:1)
  三个色**全部过亮**，白字配上去轮廓消失 —— 这正是用户说的"文本看不清"。
  现改为保留青绿-青-蓝色相、亮度压到 L≤0.169：`&H0040812C&`(4.86:1) /
  `&H0067801E&`(4.84:1) / `&H00A1792F&`(4.80:1)
- 门禁已接进 `py/music/scanner.py` 的扫描流程（`py/music/kfx_gate.py` 为内嵌副本，
  因为 `py/` 不是包，跨包相对导入会失败）。扫描后曲目数 18 → 7 ——
  拦掉 11 首不合格的，其中 Charlotte 原作因命中豁免名单不受影响
- `.git/hooks/pre-commit` 增加红线段：本次**已 staged** 的 `static/music/**/*.ass`
  若不过红线则拒绝提交（只查 staged，不扫全库，避免历史包袱阻断提交）
