# Agent Note: 硬规则要求的反问是一键流程的合法介入点, 不算失败

Status: implemented

Decision-ID: karaoke-ask-is-not-failure


## Code

- `.agents/skills/hx-anime-karaoke-ass/scripts/source/find_source.py`

## Problem

一键编排计划 (T5) 要做: 流程自己往下走, 只在硬规则要求处停下反问.
用户确认了口径: "一键" 与硬规则不冲突. 素材不达标仍要停下反问, 这是正确的介入点, 不算一键失败.

但现有脚本分不出 "该问人" 与 "坏了". `find_source.py` 实测有三处问题:

- 无达标候选时退出码 2. argparse 用法错误也是 2. 调用方无法区分.
- `--json` 模式恒返回 0. 全部不达标时也是 0, 编排器读 JSON 会静默往下走.
- 一条候选都没搜到 (网络失败或风控) 时, 也走 "反问用户". 这其实是失败, 应先按退化路径换词重搜.

后果: 编排器只能二选一. 要么把介入点记成一键失败, 逼人为过关放宽判据. 要么把失败当介入点, 把搜索故障甩给用户.

## Decision

介入点有自己的退出码与标记, 和失败分开:

| 退出码 | 含义 | 编排器怎么记 |
|---|---|---|
| 0 | 有达标候选 | 往下走 |
| 1 | 一条候选都没搜到 | 失败, 按退化路径重试 |
| 2 | 用法错误 | 失败 |
| 3 | 有候选但都不达标 | 合法介入点, 停下反问, 不记失败 |

- 退出码 3 时 stderr 打一行 `ASK<TAB>hard-rules#<条号><TAB><原因>`. 编排器与基线报告按这一行计介入点与原因.
- 文本与 `--json` 两种模式退出码一致. JSON 结构不变 (仍是候选列表), 不破现有调用.
- 达标分 40 抽成 `PASS_SCORE`, 打分与判定共用一个数.
- 口径写进 `shared/hard-rules.md` 第 13 条. 以后新增介入点也用退出码 3 加 ASK 行.

## Alternatives considered

- **什么都不做, 等编排器自己判断**: 最强理由是编排器还没写, 现在定约定可能过早. 否决: 编排器只能读退出码与输出. `--json` 恒为 0 时它没有任何信号可读, 只能去解析人看的文字.
- **复用退出码 2**: 最强理由是现有 `check_fx_profile.py` 等脚本已把 2 当 "非通过". 否决: 全仓库约定 2 = 用法或输入错误, argparse 也固定返回 2, 复用就分不开.
- **只写 `proj/ask.json` 文件, 不改退出码**: 最强理由是文件能带候选表, 信息更全. 否决: 文件要有人去读才生效, 退出码 0 时调用方根本不会去读. 候选表已在 stdout, 不需要第二份.
- **把 "没搜到候选" 也算介入点**: 最强理由是两种情况最后都可能要问用户. 否决: 硬规则第 1 条的退化路径要求先换词重搜. 网络失败直接问用户, 是把故障甩给人.

## Consequences

- 本地自测 (monkeypatch 两个搜索函数): 达标 -> 0; 全不达标 -> 3 并打 ASK 行, 文本与 JSON 一致; 无候选 -> 1; 缺参数 -> 2.
- 退出码从 2 改成 3. 曾按 `== 2` 判 "要反问" 的调用方要改. 仓库内没有这样的调用方.
- 已知边界: 不加 `--probe` 时分辨率为空, 时长吻合即可到 40 分. 这一条没改, 文档命令一律带 `--probe`.
- 其它硬规则的停点 (歌词无网络源, 出片确认) 还没接这套约定, 编排器落地时逐个接.
