# Agent Note: 逐字注音的三处静默丢失

Status: implemented

Decision-ID: karaoke-ruby-silent-loss


## Code

- `.agents/skills/hx-anime-karaoke-ass/scripts/assfx/text/anim.py`

## Problem

一次交付里同时出现三类"注音/配色静默失效", 三类的共同点是 **ASS 生成成功、校验通过、
肉眼在静态图上不易发现**, 但成片里读不出注音或读不清字。全部来自 2026-10-03 的一次用户反馈
(「注音全是错的」「有一个地方 tu yo ku 没有最后这个 ku」「「」没有完全包裹, 直接缺失了一边」
「配色根本就看不清楚…有些配色直接都配反了」)。

1. **行首的括号「被整行丢弃。**
   `lyrics.py` 的 `parse_jp` 把标点并进**前一个** unit(`units[-1]["surf"] += ch`);
   行首没有前一个, 于是 `「` 自成一个 `kind="punct"` 且 `morae=[]` 的 unit。
   到了 `layout.py` 里 `mts` 为空 → 后面 `if not mm: continue` 把这个字形跳过。
   实测: 「明りをよこせ」と奪い合い 渲染成 `明りをよこせ」と奪い合い`(缺开引号)。
2. **`[生命|=いのち]` 违反"一个汉字一个注音"。**
   熟字训用 `=` 整体标注是 `format.md` 允许的语法, 但用户对**逐字注音**的要求是硬规则
   (`shared/hard-rules.md` 第 7 条: 振假名逐字)。`生命` 读 いのち 时正确写法是
   `[生|い][命|のち]`  能拆就必须拆, `=` 只留给**真的拆不了**的(如 `今日=きょう`)。
3. **配色方向反了: 填充上彩色、描边上浅色。**
   `make_hl_color` 返回 `(色域色, lighten(色域色, 0.35))`, 而 `anim.py` 的
   `highlight()` 把它接成 `\1c{hi}\3c{glow}`  于是**填充是彩色、描边是更浅的彩色**。
   这正好撞上 `doc/KFX-RULES.md` §1 明令否掉的两条: 「填充恒为纯白, 色彩只走描边」与
   「浅色描边一律不合格」。实测 1635 条高亮事件**全部违规**:
   填充/描边对比 1.74~2.97(需 >=4.5)、描边亮度 0.19~0.41(需 <=0.1833)。

另有一处**连带失败**值得记: 改了 `lyrics.txt`(生命 4 拍→3 拍)后**没有重跑 05-align**,
于是 `timing.json` 仍是旧结构(生命=1 个 unit/3 拍), 而 `lyrics.txt` 是 2 个 unit,
`TM.get((line, unit, mora))` 全部错位  注音取到了**下一个字**的读音,
表现为"只有一半字的注音, 且读音对不上"(实测 `生命ある全ての者よ` 只出 4 条注音, 应为 7 条)。

## Decision

- **`layout.py` 处理"无音拍的孤立 unit"**: 先找前一个字(原逻辑); 若没有(行首),
  则**向后**找该行第一个有音拍的 unit, 用它  标点与紧随其后的字同时出现, 语义正确。
  **绝不 `continue` 丢字形**: 丢字是静默的, 而"标点的时机略有偏差"是可接受的。
- **逐字注音的判定收在解析层**: `parse_jp` 对 `len(kanji) > 1` 且没用 `.` 切分的写法
  发 LINT 告警(已有); 工程侧一律写 `[漢|よみ][漢|よみ]`, `=` 只在 CTE/词典都无法按字切时用。
- **配色回调改为 `hl_white_fill`**: 填充恒 `#FFFFFF`; 描边取该段色域的**深端** `stops[0]`
  (四个候选色已按 `>=4.5:1` 且 `亮度<=0.1833` 标定)。声部色只在深端色上做同族微调。
  `make_hl_color` 保留原语义(它服务的是"填充走彩色"那一类设计), **不删它**, 但在
  skill 的 `47-color` 里写明: 用 `KFX-RULES` 那套红线的工程必须用 `hl_white_fill`。
- **改 `lyrics.txt` 的标注 = 改结构, 必须重跑对齐链**
  (`align_ctc` → `kf_timing align` → `apply_fixes`)。判断依据: unit 数变了。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **给 `layout.py` 加参数让调用方决定标点怎么办**: 最强理由是"标点的时机本来就该由设计定"。
  否决: 这不是设计问题  **丢字形**在任何设计下都是错的; 而"挂到后一个字"是不坏的选择。
- **把 `「」` 加进 `PUNCT` 的并集判断**(只改 `layout.py` 那行 `s not in "？！?!、。…"`):
  最强理由是"一行就修好"。否决: 那行只是决定 `kind` 标成 `punct` 还是继承;
  **丢字的真正位置是它上面 `if not mm: continue`**。只改 kind 不改 mm 的兜底, 字照样丢。
- **删掉 `make_hl_color` 只留 `hl_white_fill`**: 否决。它服务的是另一类被文档承认的形态
  (天使の3P 那种"逐字分配颜色"), 删了等于把一条路线从库里去掉。
- **把 `美` 与 `命` 合成 `[生命|=いのち]` 以省事**: 否决。用户对逐字注音的要求是硬规则,
  而且 `い` 归 `生`、`のち` 归 `命` 是能拆的  拆得开就必须拆。

## Consequences

- 修后实测: 高亮层 **1635/1635** 条合规(填充纯白、对比 11.2~17.3、描边亮度 0.011~0.044);
  `ly:p18` 的可见文本为 `「明りをよこせ」と奪い合い`(开引号回来了);
  `生命ある全ての者よ` 的注音为 `い の ち す べ も の`(7 条, 覆盖 4 个汉字)。
- 全工程 `kanji` 型的多字 unit 归 **0** 条。
- 已知边界: "行首标点挂到后一个 unit" 让标点与首字**同时**出现;
  若要标点更早/更晚出现, 需要工程侧显式给该 unit 一个时间  库不做这个猜测。
- 已知边界: `hl_white_fill` 的描边取自 `stops[0]`(色域深端), 所以**色域的排布顺序有了语义**:
  `stops[0]` 必须是那个"能当描边"的深色。这条约束写在 `47-color` 与 `gen/common.py` 的注释里。
