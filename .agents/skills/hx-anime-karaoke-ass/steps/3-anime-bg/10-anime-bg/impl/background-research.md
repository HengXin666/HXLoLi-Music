# 番剧设定考据: 六类必查检索与 notes 写法

只看 MV 画面 + 一次泛搜就下结论, 特效只能做到"好看但空洞": 同样是守护主题, 知道角色设定的人会画魔女帽/契约红线/单翼, 不知道的人只能画通用星星与光点. 两者在技术上都是合法的 ASS, 差距全在**内涵**上  而内涵只来自读设定

所以这一步是**强制的**, 产物是 `anime.background.json`(机器证据)+ `anime.notes.md`(人读的结论). `check_gates.py` 查两者: json 存在且非空; notes **必须存在且 ≥500 字**, 缺文件判 FAIL、缺必答问题判 WARN(见 §4 与脚本注释里"为什么语义质量不做机械 FAIL")

## 0. 这一步到底在找什么: 歌是原作的隐喻

**番剧歌不是独立的音乐作品. ** 它按用途分三类, 三类都要求先读过原作

| 类型 | 例 | 没读原作会怎样 |
|------|----|---------------|
| 主题曲 OP/ED | 某番 OP | 不知道作品的核心意象(如「必须成对」的骨架) → 画不出对应图形 |
| 挿入歌 / 剧中歌 | 某番 挿入歌 | 不知道动画与原作价值观相反 → 把「寂寥」画成「温暖」, 配色方向从头就错 |
| 角色曲 | 各角色 image song | 分不清这是谁的视角 → 用错角色的符号 |

**判据**: 曲名与歌词里几乎一定有对**标题 / 角色名 / 作品固有词**的呼应.
先把它找出来  那个呼应就是"歌词"与"画面"的接点, 也就是你要做的"感情对照"

一句话分工: **MV 画面告诉你"这一段在放什么", 原作内涵告诉你"这一段该是什么情绪". ** 缺了后者, 后面十二步全做完, 也只能出一份技术正确、但不对味的字幕

## 0.5 先看邻居, 再动手搜

同一个番可能已经做过别的歌. **先查本 skill 的 `examples/`, 再查工程区 `dev/<番名>/*/anime.notes.md`**

```bash
grep -rl "<番名>" <skill>/examples/*/anime.notes.md dev/*/*/anime.notes.md 2>/dev/null
```

命中就**必读**, 并在自己的 notes 里写一行**继承声明**: 继承了哪几条母题、为什么这次不同. 跨曲引用本来就是本 skill 的加分项  同番的 ED 可以靠这一条, 把 OP 的核心母题用一根**红线**接到歌词里的对应词上. 没读过同番工程的人做不出这个连接, 反而会把已有资产丢掉、再重造一个更差的

## 1. 抓结构化条目(bgm.tv)

```bash
hx-karaoke fetch_anime_bg.py --project proj --anime "<番名>" --song "<曲名>"
# 条目不确定时先看候选表，再 --bgm-id 指定
hx-karaoke fetch_anime_bg.py --project proj --anime "<番名>" --bgm-id <id>
```

实测(2026-10-01, 未带 token): 某番条目拿到 id、简介 198 字、**26 个角色全部带中文简介**. 所以 `--bgm-token` 只是提高限额, **不是**跳过这一步的理由

产物里要用的是三样

- `summary`  故事前提. 决定了 OP/ED 的情绪基调(乡间夏日 / 轮回 / 复仇)
- `characters[].summary`  **每个角色的设定细节**. "沉默寡言、深居简出、病弱"直接给出可画的视觉母题
- `name_cn`  中文译名, 写卡片文案时用

⚠️ **`summary` 是故事前提, 不是主题. ** 主题要去 §2.5 那些地方读

## 2. 读梗与用语(萌娘百科)

萌娘百科的 `api.php` 实测返回 `{"error":{"code":"action-notallowed"}}`(只放行白名单 UA), **不要在这上面浪费重试**. 改用抓页面正文

```bash
# argo_fetch 是本机一等工具，遇 JS/风控会自动升级浏览器渲染
#   抓 https://zh.moegirl.org.cn/<条目名>，focus 用你要查的东西
```

实测两条踩坑(2026-10-01): `action=raw` 被 robots.txt 拦; 带后缀的条目名(如 `<番名>_(动画)`)**常常不存在** (返回的是"找不到页面"的正文, 不是内容  别把它当资料). 用主条目名

要查的通常是这几类(它们才是卡片与非字面特效的来源)

- **用语/梗**: 作品特有的词("缘"的多义、角色口癖). 写进间奏卡比复述 MV 标语有价值
- **角色关系**: 谁与谁是双子/主从/宿敌  决定"成对图形"(双羽、两光点、红线)用在哪句
- **章节结构**: 集数表能给"剧情走到哪"的时间感, 判断某句词对应哪段剧情
- **作品的公开主题解读**: 只当参考, 不照抄; 与 `summary` 冲突时以官方简介为准

## 2.5 检索清单: 六类必查, 一条都不能省

`fetch_anime_bg.py` 只回答"角色是谁". "**作品在讲什么**"要另外查. 下面六类, 检索词直接复制去跑(日文优先, 命中率最高); **不要只搜"<番名> 剧情"**

| 找什么 | 检索词 | 得到什么 | 写进 notes 哪一节 |
|--------|--------|---------|------------------|
| 作品解读 / 考察 | `<番名> 考察`、`<番名> 感想 テーマ`、`<番名> レビュー` | 主题、母题、演出手法 → **配色与明暗的依据** | 内核 / 主题 |
| 官方访谈 | `<曲名> インタビュー`、`<アーティスト> インタビュー` | 创作者自述的意图与听点(**权威度最高**) | 曲子在讲什么 |
| **改编差异** | `<番名> 原作 アニメ 違い`、`<番名> 原作との違い` | **动画有没有改掉原作的价值观** | 与原作的关系 |
| 题名考据 | `<番名> タイトル 意味`、`<番名> 語源` | 标题的多义, 往往与歌词同源 | 内核 / 卡片文案 |
| 舞台原型 | `<番名> 聖地巡礼`、`<番名> 舞台 モデル` | 实景地点 → 该画什么样的风景 | 母题组 |
| 乐谱 / 结构 | `<曲名> コード`(chordwiki)、`<曲名> 転調` | 段落划分 + 转调点 = **情绪曲线的机械证据** | 曲子在讲什么 |

再补两条
- 歌曲信息(发售日 / 收录曲 / 作编曲): `<曲名> シングル 収録` 或 uta-net 的歌詞页面
- 播出位置(这首歌在每话的什么位置): `<番名> 各話 エンディング 挿入歌`

**读了但没记出处 = 等于没读. ** 每条结论都要能指回具体来源(§3 的「来源」一节)

实测有效度(2026-10-01): 上面六类**全部命中**, 其中三条改变了设计方向  "改编差异"挖出动画与原作反向对置, "题名考据"挖出标题与歌词同源, "乐谱结构"挖出两次转调. 这三条**没有一条**在 bgm.tv 的角色简介里

## 3. 落成 `anime.notes.md`  四个必答问题

下一步(8b 逐句设计)会直接引用这个文件. 模板

```markdown
# <番名> 设定与母题（<曲名>）

## 内核
一句话：这部作品在讲什么。

## 主题
1~2 句，**标明出处**。（例：某作的核心意象是「必须成对」 全片母题，见原作/访谈出处）

## 与原作的关系
改编作品必答：动画相对原作**改掉了什么价值观**？（例：原作是"靠小镇的縁走出去"，
动画是"舍弃縁、两人独自沉沦"。）非改编作品写一句"原作即本体，无改编差异"。

## 曲子在讲什么
- 这是谁的视角、隐喻了谁的处境
- 曲名 / 歌词对**标题、角色名、作品固有词**的呼应（= 与画面的接点）
- 情绪曲线：逐段落写（段落 → 调 → 情绪），要有出处（访谈原话或乐谱转调）

## 角色 → 视觉母题
| 角色 | 设定关键点 | 可画母题 | 图形库对应 |
|------|-----------|---------|-----------|
| <角色 A> | 设定关键点(从条目简介抄) | 可画母题 | bird, feather, thread |
| <角色 B> | 同上 | 同上 | ring, rune_ring |

## 母题组
不属于某个角色的场景符号（夏日乡间 / 纸艺布景 / 茶色餐桌…），以及各自的使用判据。

## 继承声明
同番已有工程时必写：继承了什么、为什么这次不同。

## 画面时间线（每 1.5s 抽帧得到）
| 时间 | 画面 | 主色 | 亮/暗 | 可用的既有母题 |

## 来源
每条结论对应的 URL 或文件名。

## 未核实项
查了但没查到的，明确列出。**不许用推测填空。**
```

## 4. 判据(不满足就别进 `steps/4-kfx/42-text-main`)

- `anime.background.json`: **summary 非空 且 角色 ≥6**(`check_gates.py --min-chars`). 少于此说明抓错了条目
- `anime.notes.md`: **必须存在**且 **≥500 字**  缺文件或只写占位, `check_gates.py` 判 **FAIL**
- notes 缺"内核/主题"或"与原作的关系"、或没写出处 → `check_gates.py` 判 **WARN**(点名缺哪一节). 改编作品缺"与原作的关系"最要命, 但它影响的是**方向**不是**格式**, 所以用 WARN 点名而不是 FAIL 拦截
- ⚠️ **语义质量不做机械 FAIL**. 判"这四个问题答得好不好"要么靠人读、要么靠模型判, 都不是可证伪的检查; 硬设成 FAIL 只会催生"为了过门禁而写的空标题"那比不写更糟. 门禁只保证"做了、有出处、不是占位", **答得对不对由 `steps/4-kfx/42-text-main` 的设计表反向追责**: 设计表里每句的配色若指不到 notes 的情绪曲线, 就是 notes 没写到位
- notes 必须引用**至少一条外部解读来源**(访谈 / 考察文 / 官方资料). 只有 bgm 简介 = 没查内涵, 判 WARN
- "角色 → 视觉母题"表里, **每首歌的关键句至少能指到一个母题**; 指不到的那几句, 要么回去补查, 要么承认它只是氛围句(并在设计表里写明是氛围句)
- **情绪曲线必须有出处**: 哪段暗、哪段亮, 要能指到访谈原话或乐谱转调, 不许凭感觉
- 卡片内容与 MV 自带文字**不重复**: MV 已打英文标语时, 卡片写词源/设定/人物. 判据: 把卡片文案与逐帧抽出来的画面文字对一遍, 重复的删

## 5. 一份合格 notes 该有的密度

下面给出**四问各自的颗粒度与出处写法**. 内容必须自己去查  这一节只示范"写到多细"

**内核**: 一句话说清作品在讲什么. 一句就够, 不要铺垫.

**主题 / 题名的三层**:

| 层 | 写什么 | 出处 |
|---|---|---|
| 副题 | 作品副标题(常是英文引文) | 原著出处(篇名 + 章节) |
| 汉字表记 | 标题的官方汉字写法 | ja.wikipedia |
| 语源 | 标题词的古语多义(逐条列义项) | 古語辞典 |

**关键动作: 找「副题 / 曲名 / 歌词」三处的同一个词. ** 这条一旦成立, 它就直接决定主母题(例: 副题里的动词 = 曲名里的动词 = 歌词第 N 行的关键词). 找不到就说明还没读透

**与原作的关系**(改编作品必答): 动画有没有把原作的价值观**翻过来**?

| 维度 | 原作 | 动画 |
|---|---|---|
| 核心场所 | ? | ? |
| 与场所的关系 | ? | ? |
| 主角线走向 | ? | ? |
| 色调 | ? | ? |

填完这张表, 配色方向就定了  例如"原作是治愈的夏, 动画是寂寥的夏", 那整片色温就必须往下压, 不能全程清新. **这一步不填, 后面十二步全做完也不对味. **

还要找**演出特征**: 评论反复用什么词形容这部作品的演出手法? (如"洋画的"  短台词、玻璃上倒映的表情、背景小道具承载信息) 把它翻译成特效语汇: 玻璃反光 / 水面倒影这类安静的叠影, 而不是大而喧哗的东西

**曲子在讲什么**:
- 曲名对标题的呼应: 找出"同一个东西的两个名字", 以及**歌词里把这件事说破的那一行**  那一行是全曲脊椎, 特效重心必须落在这里
- 硬链接: 原作台词 / 标题 / 歌词三处出现同一个词
- 官方对影像的定性: 若有官方资料说明"这段影像在讲什么", 那是**有依据的**, 不是解读; 写进出处栏, 后面的抽帧结论才站得住

**情绪曲线(必须有机械证据)**: 作者访谈说走向, **乐谱往往证实且比访谈说的还多一次转调**:

| 段落 | 调 | 时间 |
|---|---|---|
| 主歌 A | 起调 | ? |
| 主歌 B | 同调或降半音 | ? |
| 副歌 1 | 升半音 | ? |
| 副歌 2 | 再升半音 | ? |

→ **半音上行就是"暗→亮"的曲线本身. 配色与亮度跟着这两级台阶走, 不要凭感觉. **

**播出位置**: 这首歌在每话的什么位置放? 决定它"接在什么情绪之后".
注意区分: 官方频道可能标 "エンディング", 制作名单写 "**挿入歌**"  两者不矛盾, **以制作名单为准**

**未核实项**: 查了但没查到的, 明确列出来. **不许用推测填空. **

## 6. 反面例子(本仓库实际踩过)

- ❌ 只搜「<番名> 剧情」拿一段百科简介 → 每个角色都只能画通用心形/星星, 全曲特效靠换配色撑
- ❌ 把 OP 画面里的"角色背影"当主角 → 那其实是配角, 特效画错母题(画了剑, 实际那集讲的是离别)
- ❌ **跑完 `fetch_anime_bg.py`、填完"角色→母题"表、门禁 PASS, 就当这一步做完了. ** 实测(2026-10-01): 26 个角色全拿到、表格填满、门禁绿, 但完全没读作品**在讲什么**  结果把"寂寥"设计成了"温暖", 配色方向从头就错. **角色表只能让特效"看得出是谁", 决定不了"这一句该亮还是该暗". ** 当时的门禁判据只有 `角色数 >= 6`, 拦不住这种失败, 所以现在加上了 notes.md 的存在性与内容检查
- ❌ **不看已有的同番工程就重头搜** → 同一个番可能已经有两份做好的 notes(含"跨曲红线引用"这种高级做法), 却从零开始查, 既丢掉现成资产, 又大概率做得更差
- ✅ 查完 bgm 角色表 + 六类检索 → 发现"成对"是全作母题、动画把原作翻了过来、情绪曲线由两次转调决定→ 每一句至少有一个"两个元素"的图形(双羽、两光点、并肩线), 副歌换成"两元素靠近/分离"的动画语汇, 后半段压成茶色. 这类设计读者说不清为什么, 但会感觉"贴"
