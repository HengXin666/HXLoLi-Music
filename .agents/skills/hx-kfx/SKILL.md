# hx-kfx — 让 AI 做出生产级 ASS 特效歌词

## 三条不被协商的契约

1. **AI 写意图, 确定性程序展开. ** 不要手写几万行 Dialogue. 实测证据: 本地东方那份成品有22013 行事件, 但唯一模板只有 73 种, 100% 都在重复; 反解后源头只有 103 个事件. 手写展开结果既不可维护, 也无法保证任何全局性质 (比如"不越界")
2. **位置全片恒定. ** 每个字的 \pos 在整个出现期间不许变, 图元层的路径坐标也不许变; 要动就用 \t 改颜色/描边/透明度. 理由见 references/normalization.md: 播放器按内容包围盒逐帧算裁剪缩放, 位置一动字号视觉大小就跟着动
3. **先测量再交付. ** 每条可判定的要求都要有一个能失败的命令. 不许"看着还行"就交

## 第 0 步 (不可跳过): 先拿到真实 MV, 按画面定位置

**不要用封面代替 MV. ** 实测: 同一首歌的画面亮度可以从 **0.002 (纯黑) 到 0.982 (纯白)**, 封面只覆盖其中**一个瞬间**

获取方式
```bash
# B 站搜索必须走 API 并带 cookie, 否则 412
curl -s -c /tmp/bili.txt -o /dev/null "https://www.bilibili.com/" -H "User-Agent: Mozilla/5.0 ..."
curl -s -b /tmp/bili.txt -G "https://api.bilibili.com/x/web-interface/search/type" \
  --data-urlencode "search_type=video" --data-urlencode "keyword=KEYWORD"
# 下载要带完整 URL, 只给 BV 号会被当无效 URL
yt-dlp --cookies /tmp/bili.txt "https://www.bilibili.com/video/BVxxxx/"
```
优先取 **NCOP/NCED** (无字幕片头片尾)  它才是特效要对位的底图

**然后逐帧测, 不要凭感觉**: 跑 `scripts/tools/mv_bands.py <视频>`  它把画面按 60px 切成横带,
对每帧求"白字最坏对比度最高"的带. 实测缘之空 OP: **最佳带的位置全片在 y=0 到 y=840 之间跳, 且只有 8/23 帧存在可读位置**

**结论**: 固定安全区不成立 (可作归一化的近似, 但不能替代按段测).
画面本身不可读的段落 (纯白/白云/强光) **必须加局部暗底**, 不能指望描边

**暗底要多黑是算出来的, 不是试出来的**: `scripts/tools/backdrop_alpha.py <带亮度>` 或喂视频.
公式 `a >= 1 - 0.183/L_m` (由 CR>=4.5 反解). 另外 **暗底必须是固定矩形不随画面动**  实测多数段落根本没有稳定暗区, 跟着画面动的暗底会闪

## 三条从 13 份本地成品逆向出的设计规律 (比标签技巧更值钱)

- **丰富感来自分层时间尺度, 不是母题种类多. ** 一个字被唱到时, 同时挂 4 到 5 个生命周期不同的效果 (幽灵层=整行 / 点亮脉冲=170ms / 回弹=480ms / 光环=619~1708ms / 粒子=800ms). 另一条同源手法: **参数随字在句中的位置递变** (环越靠后越大越慢), 比换形状更能消除机械感
- **音乐结构驱动特效. ** 实测: 凡有拖长音节 (>1s) 的句子, 紧随的情绪词窗口事件数会暴增20 倍以上; 同一个词不拖长就只有几十个事件. **触发条件是音乐, 不是词本身. ** 密度还与音频响度**无关**  它是手工配器的结果, 不是从音频特征推的
- **归一化是取舍不是真理. ** 有一份成品完全不归一化 (漂移 8837%), 但它的内部分层是: **文字层恒 \pos, 图元层允许 \move 穿屏**. 可读性靠文字层恒定保证, 视觉上限靠图元层自由换
- **密度要反向补偿句长. ** 固定每字粒子数会让长短句观感差几倍. 实测做法是快嘴句每字少给、慢句每字多给 (音节比 1:3.5, 事件比只有 1:1.6), 让每句总负荷落在同一区间
- **随机只给过程, 落点必须写死. ** `\move(随机起点, 写死终点)`  看起来即兴, 构图可预测. 配套纪律: **参数梯度用于结构** (`fscx=180-3j` 这类沿序号递变), **随机只用于底层噪声**
- **词意驱动最硬的证据形式是"段落独占", 不是"词级联动". ** 实测: 某母题 261 条 **100% 只出现在主歌1**, 而那段歌词正是「四角い箱」(方形的箱子); 另一段是**全片唯一**主色非白 (灰 #C8C8C8), 而那段唱的是「モノクロの服」(黑白制服). 判据: 统计每个母题在段落间的分布, 高度集中且该段歌词含对应关键词 = 段落级词意驱动
- **版式的纵向位置是免费的"运镜". ** 实测一份成品全片文字 y 只有 4 个值: 主歌贴顶 (y=106, 52px) 到 副歌 (y=108, 56px) 到 **终章掉到画面正中 (y=540, 60px)**, 密度同时是主歌的 4.2 倍. 只改样式表两个值, 效果是一次完整的镜头推近
- **密度分层与句长补偿必须配对, 分开用会互相抵消. ** 段落级落差 4.2 倍是"起伏"; 句级补偿 (音节比 1 比 3.5 压到事件比 1 比 1.6) 是"同段内不忽密忽疏". 只做前者会长句过浓, 只做后者则全片没有起伏
- **"不重复"来自段落级的强度包络, 不是形状多样性. ** 实测一份 42872 事件的成品: 每次爆发的粒子数取 7 个档位之一, **按段落整段不变, 与句长/字数完全无关**. 包络是`60 -> 110 -> 50 -> 70 -> 90 -> 130 -> 150`, 其中那个 110->50 的骤降正落在最内省的段落. **重复的是笔画, 变化的是气力. ** 骨架: 把歌按曲式分 5-7 段, 每段一个强度档, 段内不变
- **文字层与图元层用不同的定位标签. ** 实测一份成品 `\move` 3844 次里落在文字上的是 **0 条**; 且 `\fscx` 与 `\fscy` 出现次数**完全相同** (禁止单轴缩放). 约束的是**标签的使用权限**, 比约束坐标范围更硬  可读性从用法上被保证
- **"粒子沿轨迹飞"是打印出来的, 不是动出来的. ** 实测一份成品 30328 次 \move 里有**28113 次起点等于终点**  它把贝塞尔按弧长采样成 m 个点, 每个点放一颗静止半透明的点, 靠视觉暂留连成线. **ASS 没有"沿路径运动"的原生语法**, 这是唯一可行解

## 工作流

### 1 拿到句子与逐字时间

需要一首歌的「句 + 句中每个字的起止时刻」. 三种来源, 按可信度排

- 已有成品的 ASS: 从 Dialogue 事件聚合. **注意源文件常给每个字写多个错峰副本**, 要先按「连续相同文本去重」, 否则一句话会被拼成四遍
- 带 \k / \kf 的歌词 ASS: k 值的厘秒数直接就是逐字时长
- LDDC 之类工具: 拿到的是逐字时间, 但那是**那份音源**的时间, 必须与本地音频对齐后才能用

**元数据行必须单独过滤. ** 实测源文件里第一"句"是曲名加演唱者 (含斜杠), 如果不去掉会当成歌词渲染出来. 判据: 含斜杠、或长度明显偏离其它句、或落在开头且时长异常

### 2 用画面分析定安全区与配色

跑 scripts/tools/scene_analysis.py. 它给三样东西, **全部来自像素统计**

- 白字达标所需的底板亮度, 以及把画面压暗到多少才可行
- 主色聚类, 每簇标出对白字的对比度  从 CR 够高的暗色簇里挑描边色与局部暗底色
- 逐横条带的边缘密度, 用来挑画面最安静的纵向位置

**先读它的输出再动手. ** 实测教训: 一张普通明亮的 OP 封面, 有 90.6% 的区域达不到 12:1, 即使整体压暗到 20% 仍有 70.4% 不达标  这意味着**局部暗底是必备项, 不是可选项**

### 3 生成

用 scripts/tools/build_normalized.py, 参数是 sentences.json、safe 矩形、输出路径、描边色与暗底色. 生成器做三件事: 每字一条事件且**时长等于整行时长** (幽灵态可见, 到点用 \t 点亮)、逐句挑母题、把一切 \pos 与路径都压在 safe 矩形内. 母题库在 scripts/tools/motifs.py (16 种), 语义映射是同文件的 SEMANTIC_MAP

**安全区四边要留内缩余量** (默认 8 像素, 用 margin 参数调). 描边、阴影与字形的 overshoot 都会往外顶, 不留余量会被测出 1 到 2 像素的越界. 余量是生成器的内建参数, 不要靠手工试

### 4 渲染并逐帧测量

用 ffmpeg 的 ass 滤镜渲染成 PNG 序列, 然后跑 scripts/tools/measure_bbox.py. **它的退出码 0 才是零越界. **

渲染与测量要用**同一个背景色**, 只是写法不同 (生成器与门禁收 RRGGBB, 测量收 R, G, B)

    ffmpeg -y -f lavfi -i "color=c=0x<RRGGBB>:s=1920x1080:d=<秒>:r=<fps>" \
        -vf "ass=out.ass" -frames:v <帧数> frames/f_%04d.png
    python3 scripts/tools/measure_bbox.py --frames frames --safe <X0,Y0,X1,Y1> --bg <R,G,B>

帧率建议 8 到 10 (够看出点亮过程), 秒数取最后一句话的结束时间加两秒

它会同时打印对照数字: 同样的内容如果按逐帧包围盒裁, 缩放系数会漂移多少. 实测原型上这个漂移是 56.6% (scale 0.4912..0.8460), 归一化后是 0

看不到这一步的输出就等于没做  渲染是唯一能证伪"我以为它在安全区内"的手段

### 5 两遍收紧

第一遍的安全区按设计意图给宽裕值, 拿到实测并集后**加少量余量当正式安全区**, 再生成一次. 实测两遍把安全区从 1280x240 收到 1155x167 (面积降到 63%), 裁剪缩放从 0.3906 升到 0.4329. **字号估算与字体真实 advance 不可能精确一致, 逐帧实测是唯一可靠的收敛手段. **

### 6 质量门禁

跑 scripts/gates/gradient_gate.py 与 scripts/gates/contrast_check.py, 两条都必须退出码 0

**从别人成品里统计手法规模之前**, 先跑 scripts/gates/lint_events.py  实测成品里存在** 未求值的模板占位符** (渲染 0 像素) 与**零/负时长事件** (libass 静默丢弃), 它们占了事件数却不产生画面. 不先清掉就会把"写了多少"当成"播了多少". **分析别人的成品时**先跑 scripts/gates/move_probe.py: 它判断那份作品的`运动"是真位移还是逐帧打印(实测三份成品的同点 move 占比从 0% 到 92.7%, 区分度很高). gradient_gate 的三条判据是: 母题种类数与最高频占比、静止事件占比、**整行内按字序的点亮时刻严格递增且首末不越界**. 阈值与实测基准见 references/checklist.md

### 6.5 想知道"这个手法值多少"就做消融对照

复制一份, 逐个删掉某类事件, 重新渲染**同一帧**, 比较像素数与文件体积. 这是回答"这个设计为什么必要"的实证解法, 而不是审美判断

实测过的结果最说明问题
- 删"花海" -> 同帧像素 **-40.1%** (副歌与主歌的区分度消失)
- 删"闪光" -> 同帧像素**只 -1.1%**, 但它是全片唯一的高光点  **面积占比与观感权重不是一回事**
- 删"33ms 弹跳" -> **单帧 0 变化**, 因为它只存在于时间维度

**最后一条是关键: 有一类手法在静态截图上完全测不出来. ** 评估特效不能只看截图, 必须看连续帧

### 7 抽帧自己看

**最后一步不可省, 也不可外包给脚本. ** 门禁能验边界、种类数、点亮顺序, 验不了"绚烂"和"贴合画面". 抽至少三个不同段落的首帧/中帧/末帧, 逐张看过再交

## 环境

脚本依赖 numpy 与 pillow; ffmpeg 需要带 libass 的构建 (用 ffmpeg -filters 查 ass 滤镜确认). 用仓库已有的虚拟环境跑, 不要新建
