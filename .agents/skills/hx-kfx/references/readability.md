# 可读性: 具体数字与门限

## 门限 (WCAG 2.1, 不要四舍五入)

| 对象 | 门槛 |
|---|---|
| 填充 / 描边 | >= 4.5:1 |
| 填充 / 背景 (底板压暗后) | >= 12:1 |
| 幽灵态 / 背景 (整行未点亮时) | >= 3:1 |

**描边亮度的硬上限是 0.1833** (纯灰约 RGB <= 118). 描边必须比中灰更暗, 否则白填充没有清晰轮廓. 浅色描边一律不合格  实测过的反例: 浅蓝 (168,216,248) 对白填充只有 1.52:1, 渲染出来轮廓完全糊掉

## 幽灵态怎么取值

"整行先出现再逐字点亮"要求未点亮的字**必须看得见**. 但暗态越亮越可读, 亮暗差越小, "点亮" 越不明显. 实测的平衡点在**暗态亮度 0.15 到 0.20 (灰阶 108 到 123)**

| 灰阶 | 对深色背景 (11,16,22) |
|---|---|
| 89 | 2.73:1 太暗 |
| 108 | 3.64:1 可用下限 |
| 123 | 4.51:1 推荐 |
| 148 | 6.29:1 亮暗对比不足, 失去"点亮"的意义 |

本 skill 的生成器默认用灰阶 123

## 描边色从哪来

**不要凭空选, 从 MV 主色的暗色簇里挑** (见 scene-driven.md). 理由是可读性与画面贴合可以同时满足: 实测那张东方封面里 #325669 对白字是 7.86:1, 同时它本身就是画面的主色之一

参考: 一份生产级成品 (Charlotte) 的做法是**白填充 + 每段换一个饱和的中间调彩色描边**, 四种描边色对白填充分别是 7.81 / 6.84 / 2.37 / 5.43. **注意它自己也有一色只到 2.37:1**  说明动效场景下 2.37:1 勉强能用, 但那是下限, 不是目标

## 两个必然会踩的解析坑

### lstrip 是字符集不是前缀

strip 系列剥的是"字符集合里的任意字符". 对 `"0B1016"` 调用 lstrip 传 `"0x"`, 会把开头的 0 和 B 都剥掉, 得到 1016, 之后所有解析都是垃圾. **用 startswith 判断, 别用 lstrip. **

### ASS 的 &HBBGGRR& 与网页的 #RRGGBB 顺序相反

混用会静默把红蓝对调: 同一个 0B1016 当作网页色是 RGB(11,16,22), 当作 ASS 色是 RGB(22,16,11). **背景解析错一个色序, 所有对比度数字全部失真. **

scripts/gates/contrast_check.py 两种写法都接受 (&H 开头按 ASS 逆序, 否则按网页顺序), 就是为了避免这个坑

## 反验证: 检查器给出 PASS 之后要拿已知答案反验它

## 幽灵态默认不会被自动测

用 `--ass` 模式读样式时, 幽灵态是**行内标签** (`\1c`) 而不是样式表里的值, 所以脚本读不到它, 必须显式传 `--ghost`. 默认跑法会漏掉这条判据  生成器默认用的灰阶是 123

## 反验证样本: 填充 FFFFFF、描边 91276F、背景 0B1016、幽灵 7B7B7B,
应当输出填充/描边约 7.71:1 (梅紫)、填充/背景约 19.09:1、幽灵/背景约 4.51:1. 偏差超过 0.1 就是解析错了
