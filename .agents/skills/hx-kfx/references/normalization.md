# 归一化: 把特效钉进一个固定矩形

## 它解决的是什么问题

播放器的歌词悬浮窗默认只有 500x350, 而 ASS 在 1920x1080 画布上渲染. 所以必须"先裁出内容区, 再缩放进窗口". 这一步本身没错, 问题是**裁剪窗口是时间的函数**

    scale = min(窗口宽 / 内容宽, 窗口高 / 内容高, 1)

内容高矮一变, scale 就变, 字号的视觉大小跟着变. 实测 18 份真实成品的时间轴

- 单曲之内, scale 的相对跨度最小 0.208, 最大 1.460
- 相邻采样点之间**单次最大跳变 0.6029**  一次采样间隔里字号视觉大小变 60%
- 曲目之间的 scale 中位值从 0.2606 到 1.0000, 相差 3.84 倍

所以"轻微偏移震荡"只是表象, 底下还有一层: 同一首歌里字忽大忽小, 不同歌里大小不一致
## 契约

**所有 FX 行的绘制范围必须落在同一个固定矩形内, 且全片不变. **

做到之后缩放系数退化成常量. 以 1600x420 的框为例恒为 0.3125; 本轮实测的安全区 1155x167 恒为 0.4329

## 代价 (必须一起说)

- **放弃超框的表现**: 全屏扫光、边缘飞入、跨整屏的位移线, 都做不了
- **安全区越大字越小**. 裁剪缩放受限于更紧的那一维, 而歌词加母题本来是横条(实测约 5.3 比 1), 窗口是 1.43 比 1, 于是宽度永远不是瓶颈, **高度才是**. 1280 宽的安全区把 68px 的字压到约 27px
- **归一化不是无条件放大**. 它是用"恒定"换掉"中位更大但会漂移": 实测动态裁剪的中位 scale 比归一化的常量还大 30.9%, 但它会漂移 56.6%. 选择归一化是接受一个稍小但稳定的字号

因此安全区应当在**够放下最大特效**的前提下尽量紧凑, 而不是尽量大
## 起点取多少 (不要靠感觉)

没有"正确答案", 但有一个有依据的起点公式

    X0 = (1920 - W) / 2          Y1 = 1080 - 40
    Y0 = Y1 - H                  (H 先按"文字带 1.27 + 母题带 0.50"倍字号估)

从 **字号的期望值倒推 H**, 而不是先定 H 再让字号被压. 经验起点: 主字号 68px 时H 取 150 到 240, W 取 1000 到 1400. 每句字数多则加大 W

第二遍收紧后的框仍会比实测并集大一圈 (实测给 823x122 的框、内容只用 702x88), 这是正常的  余量是为不同句子之间的差异留的. **不需要第三遍**: 再收就会出现"长句越界、短句正好"的反复, 且收益是线性的而风险不是

两级余量要分清: **安全区自身的余量** (两遍法用的水平 16 / 垂直 12) 与**生成器内缩余量** (--margin, 默认 8) 是两件事, 后者管描边/阴影外扩, 前者管句子间差异

## 两遍法

1. 第一遍按设计意图给一个宽裕的矩形, 生成并逐帧渲染, 量出内容并集
2. 取并集加少量余量 (实测水平 16 像素、垂直 12 像素) 作为正式安全区, 重新生成

不能一遍到位的原因: 字号自适应、字形宽度估算 (全角按字号、半角按一半) 与字体真实的 advance 宽度不可能精确一致. 实测第一遍 1280x240 落到并集 x[396,1519] y[866,1009], 收紧到 1155x167 后重测并集 x[447,1465] y[906,1020], 两次越界量都是 0

## 怎么验

跑 scripts/tools/measure_bbox.py. 它逐帧扫非背景像素求包围盒, 判据是**四个方向的越界量全为 0**

两个实现细节不能改

- **用"与背景色的通道差之和"而不是固定灰度阈值**. 幽灵态文字与背景的差异很小, 固定阈值会把幽灵态判成空帧, 于是漏掉"整行先出现"的反例
- **背景色要传对**. 渲染时用什么底色, 测量时就传什么底色

## 只对"预处理"路径成立

播放器只有开着预处理时才用 1920x1080 画布; 不预处理时渲染画布就是窗口尺寸, 根本没有裁剪. 因此固定安全区只在那一条路径上有意义, 也不会自动惠及其它路径. 做之前先确认目标路径
